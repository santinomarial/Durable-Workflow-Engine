# Control-plane security

The HTTP control plane defaults to fail closed. Starting the API without valid
authentication configuration fails during application startup. Authentication
may be disabled only by explicitly setting `DWE_AUTH_MODE=disabled`; use that
mode solely for an isolated local development environment.

## Provision keys

Generate a high-entropy bearer token and its non-secret configuration entry:

```shell
uv run engine auth-key --key-id oncall-admin --role admin
```

The command prints the token once and a `configuration` value containing only
its SHA-256 digest. Put the token in a secret manager and give it to the
operator through an approved secret-sharing channel. Configure one or more
comma-separated digest entries on the API service:

```shell
export DWE_AUTH_MODE=required
export DWE_API_KEYS='dashboard:viewer:DIGEST,oncall:admin:DIGEST'
```

Key IDs may contain letters, numbers, hyphens, and underscores. The configured
digest is safe to compare without retaining the bearer credential, although it
should still be kept with deployment configuration. The service compares
digests in constant time. Rotate a key by deploying the old and new digests
together, moving clients, and then removing the old entry.

The console asks for a token and keeps it only in tab-scoped `sessionStorage`.
It sends the token in the `Authorization: Bearer` header, so browsers do not
attach it implicitly and cross-site request forgery does not apply. A strict
content security policy and injection-safe rendering reduce token exposure;
TLS is still mandatory at the ingress because bearer tokens are credentials.

## Roles

| Role | Permissions |
| --- | --- |
| `viewer` | Inspect executions, history, and fleet statistics |
| `operator` | Viewer permissions plus start, signal, cancellation, visibility editing, pause/resume, and dead-letter inspection |
| `admin` | Operator permissions plus termination, retry-as-new, metrics, and API audit access |

Every successful or duplicate control-plane mutation appends an immutable audit
record in the same PostgreSQL transaction as the workflow transition. Audit
records include the server request ID, key ID, role, action, workflow ID,
acceptance result, and non-payload metadata. Signal and workflow payloads are
excluded to avoid duplicating sensitive business data.

## Request protection

- `DWE_MAX_REQUEST_BYTES` bounds both fixed-length and streamed request bodies;
  the default is 1 MiB.
- `DWE_RATE_LIMIT_PER_MINUTE` limits requests per authenticated key in each API
  process; the default is 300. Enforce a shared limit at the ingress when
  running more than one API replica.
- `/api/health`, the static console shell, and OpenAPI documentation are public.
  Workflow data and every control endpoint require a valid key.
- Terminate TLS at a trusted ingress and do not expose the application port
  directly to untrusted networks.
- Request IDs are generated by the server and returned on all normal API
  responses for log and audit correlation.
